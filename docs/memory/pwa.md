PWA shell: Workbox service worker (vite-plugin-pwa, prompt-to-reload), self-hosted fonts, inline boot placeholder and generated iOS launch images; `/api` is never cached.

- **Service worker** is generated at build time by `vite-plugin-pwa` (`generateSW`, config in `frontend/vite.config.ts`). It precaches everything in `dist` except `public/splash/`, the 512px icons, the latin-ext/cyrillic-ext/vietnamese font subsets and the `.woff` fallbacks (`globIgnores`). A file over the 2 MiB precache limit fails the build; keep it that way (don't set `showMaximumFileSizeToCacheInBytesWarning`). `public/manifest.webmanifest` is the manifest (`manifest: false` in the plugin).
- **`/api` is never touched by the worker**: `navigateFallbackDenylist: [/^\/api\//]` and no runtime caching. Offline, the shell loads and the launch refresh fails: with a session hint the app stays up on its persisted cache (see below), without one it lands on the sign-in page. Don't add runtime caching for API responses without a plan for stale data and auth.
- **Updates prompt, never auto-reload** (`registerType: 'prompt'`): a silent reload would lose an in-progress workout. `src/pwaUpdatePrompt.tsx` registers the worker via `virtual:pwa-register/react` (after the load event), checks for a new `sw.js` hourly and on `visibilitychange` to visible, and shows `src/pwaUpdateBanner.tsx`. Two plugin behaviours are overridden there: its unconditional reload on takeover (`onNeedReload` is a no-op; a `controllerchange` listener reloads only the tab whose Reload was tapped and shows the banner in the others), and workbox-window reporting only the first update per page lifetime (`watchForUpdates` follows every `updatefound`). A dismissed update activates once every tab of the app is closed.
- **Banner placement**: it is mounted outside the router (`main.tsx`), so it measures whichever bar is pinned to the bottom (tab bar, workout bar, Log Save bar) and sits 8px above it; z-20 keeps it under the pages' own toasts.
- **Production only**: `main.tsx` renders `<PwaUpdatePrompt />` behind `import.meta.env.PROD`; `devOptions.enabled: false`, so `vite dev` has no worker (the virtual module is a no-op stub there). Tests mock the virtual module (`PwaUpdatePrompt.test.tsx`). To try the worker locally: `corepack pnpm build && corepack pnpm preview` (localhost is a secure context; any other plain-HTTP origin gets no service worker).
- **Retiring or fixing a broken worker**: deleting `sw.js` doesn't remove installed workers (a 404 on update leaves the old one running). Ship a fixed build, or vite-plugin-pwa's `selfDestroying: true`, and keep it deployed until clients have updated.
- **nginx** (`frontend/nginx.conf`): `index.html`, `/sw.js` and `/manifest.webmanifest` are `no-cache`; `/assets/` is `max-age=31536000, immutable` and 404s instead of falling back to `index.html`. gzip is on (the stock nginx:alpine config has it off).
- **First paint**: `index.html` has an inline `<style id="boot-style">` (brand background) and a logo placeholder `#boot-splash` inside `#root`, which React replaces on mount with the identical `BootSplash` component while auth resolves (below). The CSS bundle still blocks rendering, so this covers the wait for the JS bundle, not for the CSS. The wordmark's Montserrat 700 is preloaded from `index.html` so the placeholder doesn't paint in a fallback font.
- **App icons**: `node scripts/generate-icons.mjs` (from `frontend/`) renders the SVG artwork in headless Chromium and writes `public/apple-touch-icon.png`, `public/icons/*` and the favicons. The Apple icon is full-bleed and draws no corners or rim of its own: iOS clips it with its squircle mask, and a drawn rounded rim (circular corners) was cut off-centre by it. The recessed plate inside the frame, and the standalone `icon-*.png` tile, use a superellipse (`squirclePath`, n = 5) that stays concentric with that mask. The clay pieces use the 'slab' height profile (rounded shoulder, flat top); crest-high domes looked like wet soap at Home Screen size. The maskable variant has no plate (its outer 10% can be cropped to any shape). iOS caches the icon when the app is added to the Home Screen, so re-add it to see a new one.
- **iOS launch images**: `node scripts/generate-splash.mjs` (from `frontend/`) screenshots that placeholder in headless Chromium at every iPhone/iPad screen size, writes palette PNGs to `public/splash/` and rewrites the `apple-touch-startup-image` links between the markers in `index.html`. Re-run it after changing the placeholder or to add a device (edit `PHONES`/`TABLETS`). Needs Playwright's Chromium, like `generate-icons.mjs`. iOS reads the launch image when the app is added to the Home Screen, so an existing install may need re-adding to pick up a new one. Not verified on a device: with status bar style `default` the page may start below the status bar, which would put the placeholder logo about half a status bar lower than in the launch image.

## Launch: session hint, optimistic render, persisted cache

- **Session hint** (`src/lib/sessionHint.ts`): localStorage `trainlytics:session` holds the username of the account signed in on this browser. Written on login and on every successful refresh; removed on logout and when a refresh is refused (only if it is still that account's, so an expiring tab doesn't drop another tab's hint). Storage errors (Safari private mode) mean no hint, i.e. the pre-hint behaviour. Other tabs hear changes through the `storage` event: when the hint stops naming a tab's account (logout or another account signed in elsewhere), that tab signs out too, leaving the device's shared settings (rest length) to the tab that logged out. A refresh that resolves after another tab changed the hint (before its storage event arrives) is not adopted: the tab signs out instead of writing its account back over the other tab's.
- **Optimistic render**: with a hint, `AuthProvider` starts as `{ token: null, username: <hint>, isLoading: true }` and `ProtectedRoute` renders the page at once (after the cache restore below). Without one it renders `BootSplash` (same markup as the inline `#boot-splash`, kept identical by `BootSplash.test.tsx`) until the refresh settles; `LoginPage` shows it too while `isLoading`, and redirects to `/today` for a token or a remembered username. In `useAuth()`, "`isLoading` with a username" means a remembered session still resolving; "username without token" after that means the server couldn't be reached.
- **One launch refresh** (`lib/api.ts` `refreshSession`, single-flight per session epoch, 15 s timeout): `AuthProvider` starts it once per mount (a ref, so StrictMode's effect replay joins it) in a layout effect. Any request without a token first calls `refreshSession()`, which joins the one in flight: optimistically mounted pages send their first requests with the new token, one refresh, no 401s. `/auth/*` never waits. Results: a token, `unauthorized` (401 only: the session is over) or `unavailable` (offline, timeout, 403/5xx). Only `unauthorized` logs out, reported by whoever started that refresh (`AuthProvider` at launch, else the request). `unavailable` keeps the session and its cached data; the request fails with "Could not renew the session…" without being sent, and the next one tries again. Every new token reaches `AuthProvider` (`setSessionRefreshedHandler`), so `useAuth().token` follows refreshes; the Apple Health XHR upload calls `getAccessToken()` when it has none.
- **Requests are bound to their session**: `setToken(null)` (logout, expiry, an account switch) bumps a session epoch. After every send and every refresh, a request that started under an older epoch stops: it is not re-sent (a refresh that returns another account never replays A's request as B), its 401 reports nothing (it can't sign out the next account) and its answer is dropped (it can't land in the next account's cache). A refresh started under an older epoch is not joined by the next session's requests. `AuthProvider` binds the launch result and a logout's completion to the epoch they started in, so neither acts on a later session. Logout waits for a refresh in flight, then `blockRefresh()` stops new ones until the next login (`setToken(<token>)`) before `POST /auth/logout`, because a refresh answered after it would re-set the refresh cookie. A 401 from `/auth/*` (wrong password) never runs the unauthorized handler. `forgetAccount` remounts the tree only when an account was signed in. The Apple Health upload is not sent without a token (`getAccessToken()` returns null when renewal fails or the session changed meanwhile).
- **Persisted query cache** (`src/lib/queryPersist.ts`, `PersistQueryClientProvider` in `main.tsx`): IndexedDB via idb-keyval, key `trainlytics:query-cache:<username>`. Persisted: queries with data no older than 7 days (a query whose last refetch failed is saved with its last good data, as success, so an unreachable server doesn't empty the next launch); no mutations. `maxAge` 7 days and the QueryClient's `gcTime` the same (a shorter gcTime drops restored queries from memory and so from the next save). `buster` is `__BUILD_ID__` (git short SHA + build time, `define` in `vite.config.ts`, `src/buildId.d.ts`), so every build starts once with a cold cache. After a restore, `finishRestore` marks every query invalidated: restored data shows at once and is refetched on first use, including `staleTime: Infinity` queries (last-session defaults), which before persistence were fetched fresh each launch. `ProtectedRoute` shows `BootSplash` while restoring (`useIsRestoring`), so a page paints with its data instead of a skeleton; a stuck IndexedDB read gives up after 2 s. Today keeps its last plan on screen when a refetch fails; other pages still show their error state once retries run out.
- **Account isolation**: the persister works for its owner (`setPersistedCacheOwner`, set by `AuthProvider` from the hint at launch and on every login/refresh) and only while the owner is also the session hint. Each account has its own throttled writer, and a snapshot goes to the writer of the account that owned the cache when the snapshot was taken; it is dropped if that account no longer owns the cache when the write happens. `forgetAccount` (logout, refused refresh, a refresh or login for another account, another tab's logout) ends the api session, clears the owner, then `queryClient.clear()` (so the snapshots clearing produces belong to nobody), deletes the leaving account's entry and remounts everything under `AuthProvider`, so no page keeps the old account's data on screen or in its state. A restore whose owner changed while IndexedDB was reading restores nothing, and `finishRestore` drops what was hydrated if the owner changed after the read.
- **Known limits** (found in review, not handled): a mutation's own `onSuccess` (e.g. `setQueryData`) that runs after its session ended can still write to the cache; the request-level epoch check closes this except within the same microtask turn, which a refresh (a network task) can't reach. An IndexedDB write whose connection was still opening can land after another tab deleted that account's entry (it holds that account's own data; it is only restored for that account). A refresh in another tab can race a logout and re-set the cookie (no cross-tab lock); so can an offline logout, which can't reach the server (pre-existing). `useRestLength` reconciles once against the restored profile before the fresh one arrives, and ProfilePage re-syncs its form when the fresh profile replaces the restored one. Also: with a hint, the last account's cached data is on screen for one refresh round trip before an expired session sends the user to sign-in, and indefinitely while offline (the server can't be asked). A tab still running a bundle from before this release doesn't clear the hint or the persisted cache on logout. Workout drafts in localStorage (`trainlytics_draft_*`) are not per account and survive logout (pre-existing).
